# 1. 报告结论与战略选择

## 1.1 你的核心问题不是“基础差”，而是“知识碎片化、工程闭环不足”

你已经拥有：

- 中国机器人创意大赛轮式格斗擂台赛经历；
- RoboMaster哨兵机器人调试经历；
- STM32基础；
- FreeRTOS任务创建与基本使用经验；
- F4主控板独立原理图/PCB设计能力；
- 港科大2024超级电容复刻经历，并正在重新复刻；
- OpenCV基础；
- Jetson端YOLO目标检测模型部署经验；
- Linux基本操作；
- 对Makefile、make、gcc、gcc-arm交叉编译已有基本认识；
- H7主控板；
- Jetson；
- 海康工业相机；
- MID360S激光雷达；
- 双目相机；
- i.MX6ULL正点原子ALPHA Linux开发板；
- RoboMaster实验室设备和整机条件。

这套资源与经历并不弱。

真正的问题是：

1. **很多知识停留在“用过”而不是“理解并能解释”。**
2. **项目很多是调试、复刻、比赛框架上的二次工作，缺少完全由你负责的系统闭环。**
3. **缺少工程证据：测量数据、波形、测试报告、Bug记录、版本记录、设计文档。**
4. **技能方向过多，容易继续扩散。**
5. **你已经有“机器人系统广度”，但还没有形成一个足以支撑求职的“技术深度锚点”。**

因此未来十个月的核心不是“再学十门新技术”，而是：

> **把已有经历重新工程化、底层化、证据化。**

# 6. 学习方式必须发生的改变

过去常见模式：

```text
看教程
→ 跟着敲
→ 跑起来
→ “我会了”
```

未来必须变成：

```text
问题
→ 查官方文档 / Datasheet / Reference Manual
→ 自己形成假设
→ 实验
→ 示波器 / Logic Analyzer / GDB / Log验证
→ 记录数据
→ 总结根因
→ Git提交
→ 写文档
→ 用面试题反向验证理解
```

## 每一个知识点必须形成五种证据

1. **我能解释**
2. **我能写出来**
3. **我能测出来**
4. **我能Debug**
5. **我能写成文档**

只满足“代码能运行”，不算真正完成。

## 7.2 必须做到的效果

不要以“看完多少课”为标准。

### 验收标准

你应该能：

- 不看教程独立配置UART DMA接收；
- 写一个Ring Buffer；
- 独立实现一个简单协议Parser；
- 用逻辑分析仪验证UART/SPI/I2C时序；
- 用GPIO翻转 + 示波器测定某段代码执行时间；
- 能解释中断优先级；
- 能解释DMA为什么降低CPU负担；
- 能解释`volatile`能做什么、不能做什么；
- 能解释`.data`与`.bss`区别；
- 能解释HardFault基本排查思路；
- 能根据Reference Manual自己找到外设配置关键寄存器。

---

## 7.3 F4与H7怎么分工

### F4

用于重新建立基础。

优点：

- 系统较简单；
- 资料多；
- 不容易被Cache/MPU等高级问题干扰。

### H7

用于旗舰项目。

后期重点学习：

- DCache/ICache；
- DMA Cache Coherency；
- Memory Domain；
- MPU基础；
- 更复杂的FDCAN/高速外设。

这样H7不会变成“莫名其妙出Bug的板子”，而会变成面试加分项。

---

## 7.4 AI怎么结合

AI适合：

- 根据Reference Manual某一章节帮你整理阅读问题；
- 帮你解释启动文件；
- 把反汇编代码转成可理解的执行过程；
- 给你的C代码做静态Review；
- 生成边界测试用例；
- 模拟面试官追问。

AI不应该：

- 直接替你生成整个驱动，然后你复制；
- 在未看Datasheet情况下相信其寄存器地址；
- 替代示波器/逻辑分析仪验证。

### 推荐AI工作流

# 8. P0：FreeRTOS从“会用”到“真正理解”

当前你最应该重点补的知识之一就是FreeRTOS。

官方文档明确区分Running、Ready、Blocked、Suspended等任务状态；Blocked任务不会占用CPU运行时间。[S9]

Mutex包含优先级继承机制，但优先级继承只能减轻Priority Inversion，并不能从根本上解决所有优先级反转问题。[S10]

Cortex-M上的FreeRTOS问题中，中断优先级配置错误是一个非常典型的故障来源。[S11]

## 8.2 必须亲手做的实验

### 实验1：任务调度

### 实验2：Blocked vs Busy Wait

对比：

```c

```

和

```c

```

观察CPU行为。

### 实验3：Queue

ISR接收数据 → Queue → Task处理。

### 实验4：Task Notification

与Queue做简单性能/代码复杂度对比。

### 实验5：Priority Inversion

主动构造：

低优先级拿锁

→ 中优先级抢占。

观察Mutex Priority Inheritance。

### 实验6：Stack Overflow

### 实验7：错误中断优先级

完成后Merge。

Git官方文档支持通过branch组织并行开发工作。[S16]

---

## 17.5 Commit怎么写

不要：

```text
update
修改
123
final
final2
```

应该：

```text
feat(can): add motor heartbeat monitoring

fix(freertos): prevent queue overflow in uart rx path

test(control): measure 1kHz task jitter with DWT

docs(supercap): add low-voltage bring-up checklist
```

---

## 17.6 Release

每个重要阶段打Tag：

```text
v0.1-bringup
v0.2-can-control
v0.3-rtos
v0.4-ros2-integration
v1.0-demo
```

让项目有“产品成长轨迹”。

## 17.7 Git中不要放

- 私钥；
- 密码；
- 大数据集；
- 大模型权重；
- 未获授权的实验室/队伍私有代码；
- 别人的开源代码但不标许可证来源。

如果基于港科大或其他开源项目：

> README里明确写清楚Upstream、License、你修改了什么。

诚信本身就是工程能力。

# 18. 如何把AI真正融入你的学习和工程流程

未来工程师不应该拒绝AI，也不能依赖AI。

你的目标是形成：

# **AI-assisted, human-verified engineering**

---

## 18.1 AI的八个角色

### 角色1：私人教师

例如：

> 我正在学习Cortex-M异常机制。我目前理解如下……  
> 请不要直接给我完整答案，先指出我的理解中哪三处最可能有错误，再告诉我应该查ARM手册的哪些关键词。

这种用法非常好。

---

### 角色2：代码审查员

输入：

- 代码；
- 设计约束；
- MCU；
- 是否ISR；
- 实时要求。

让AI检查：

- Race；
- Null；
- Overflow；
- ISR Safety；
- Blocking；
- Memory；
- Boundary。

但你自己决定是否修改。

---

### 角色3：Debug假设生成器

不要问：

> “为什么不工作？”

而要给：

- 现象；
- Log；
- 波形；
- 最近代码Diff；
- 已排除条件。

让AI输出：

```text
Hypothesis
Probability
Evidence
How to Test
Expected Result
```

这会极大提高你的Debug效率。

---

### 角色4：测试工程师

让AI生成：

- 正常测试；
- Boundary；
- Fault Injection；
- Disconnect；
- Timeout；
- Overflow；
- Power Cycle；
- Long Run。

AI特别适合帮助你想到“异常场景”。

---

### 角色5：文档编辑器

你的内容自己写。

让AI帮助：

- 改结构；
- 找逻辑漏洞；
- 简化语言；
- 生成Mermaid草图；
- 统一术语。

不要让AI凭空生成你没做过的数据。

---

### 角色6：面试官

每学一个模块：

让AI进行：

```text
第一轮：基础问题
第二轮：项目追问
第三轮：故障场景
第四轮：设计权衡
```

并要求：

> 不接受背定义，持续追问“为什么”。

---

### 角色7：JD分析器

以后每周收集10～20个目标JD。

让AI统计：

- 高频技能；
- MCU；
- RTOS；
- Linux；
- C++；
- CAN；
- ROS2；
- Git；
- 学历；
- 行业。

然后更新学习权重。

---

### 角色8：简历审查员

把JD和你的简历一起输入。

让AI：

- 找关键词缺口；
- 判断哪些项目经历与岗位相关；
- 帮你重写表达。

但是：

**禁止让AI制造你没有的经历或指标。**

---

## 18.2 AI使用的“五步校验法”

任何技术问题：

```text
AI提出答案
↓
确认它引用的概念
↓
查官方文档/Datasheet
↓
实验验证
↓
记录结论
```

核心原则：

> **AI提供候选解释，仪器与官方资料提供证据。**

---

## 18.3 各模块如何结合AI

| 模块 | AI最适合做什么 | 不能交给AI什么 |
|---|---|---|
| STM32 | 解释手册、Code Review、测试用例 | 寄存器配置真实性必须查RM |
| FreeRTOS | 调度推演、Race检查、面试追问 | 实时行为必须实测 |
| 超级电容 | Checklist、Datasheet比较、测试计划 | 安全、电气设计和上电判断 |
| ROS2 | CMake/接口解释、QoS对比 | 系统是否实时稳定必须自己测 |
| YOLO | 日志分析、实验设计、部署错误分析 | Accuracy/Latency不能靠AI猜 |
| Linux Driver | API解释、代码Review | Kernel行为必须查文档和运行验证 |
| Git | Commit/Release Note辅助 | 哪些代码可以公开需要你判断 |
| 求职 | JD聚类、模拟面试、简历润色 | 不得造经历 |

# 结束语

你现在并不是“什么都不会，需要重新开始”。

真正需要发生的改变是：

> **从“参加比赛并接触技术”转变为“能够独立设计、验证和解释工程系统”。**

未来十个月请持续问自己四个问题：

1. 这个东西我只是跑起来了，还是我能解释？
2. 出Bug以后，我能不能用工具找到根因？
3. 我有没有真实测量数据证明它？
4. 如果明天面试官让我从零解释这个系统，我能不能把架构、权衡和失败经历讲清楚？

如果四个问题都能回答“能”，这项能力才真正进入你的简历。

你的目标不是成为“会最多技术名词的本科生”。

而是成为一个面试官看完项目后愿意继续追问的人：

> **这个学生真的自己做过，而且知道自己为什么这样做。**
